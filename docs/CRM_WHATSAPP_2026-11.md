## Что сделано (по просьбам владельца)
1. **«Обращения» в Статистике** = сколько людей написало (чаты) за период, а не заказы.
   - Карточка: Таргет / Органика / Повторные; API `GET /api/inquiries`.
   - Решение владельца: не каждое обращение превращать в заказ.
2. **«Разослать все треки (N)»:** одна кнопка в CRM рассылает трек-номера всем клиентам с загруженным треком, через подключённый WhatsApp.
   - Показывает прогресс «Отправляем… x из y».
   - Если подключения нет, предлагает ручную отправку.
   - API `POST /api/orders/:id/send-track`.
3. **Ночные / утренние клиенты не теряются:**
   - Сообщения, пришедшие пока программа была выключена, считаются новыми, а не историей.
   - Нерасшифрованное сообщение клиента приходит в CRM заглушкой «Сообщение не расшифровалось — откройте этот чат на телефоне». Потом настоящий текст заменяет её и определяет источник (таргет / органика).
   - Чат, впервые пришедший через историю, но начатый ≤ 72 ч назад, считается новым клиентом.
4. **Надёжность программы:**
   - Файлы сессии пишутся атомарно.
   - Остановка мягкая: программа дожидается записи.
   - Обновление стартует не раньше чем через 10 минут после запуска; раньше перезапуск при обновлении терял ночные сообщения.
   - Живые сообщения идут в CRM раньше большой загрузки истории.
5. **«Ожидание сообщения» у клиента / одна серая галочка на рабочем телефоне.** Программа хранит свои последние 500 отправленных сообщений (7 дней) и пересылает их, когда телефон клиента или наш телефон просит повтор. В логе это строка `retry: resending…`.
6. **10.11: с 07.11 входящие не доходили, трек-сообщения «ожидали».**
   - Причина: после подключения очередь обработки Baileys зависала (загрузка истории без тайм-аута). Ничего не обрабатывалось, а через 50 минут WhatsApp сам рвал соединение («Stream Errored (ack)»).
   - Исправлено: тайм-аут 60 с на все загрузки; сторож — если обработка висит дольше 3 минут, переподключение; задержанные события выпускаются.
   - После обновления (552ce37) сегодняшние 2 потерянных чата пришли сами.
7. **Ярлык «Bikas WhatsApp»** на рабочем столе создаётся автоматически.

## Если клиенты снова не появляются в CRM
1. Проверить в CRM: Настройки → «Подключение WhatsApp». Должно быть «На связи» и версия.
2. Попросить у владельца лог. Самый простой способ: открыть папку (ярлык «Bikas WhatsApp»), открыть `connector.log` Блокнотом и прислать конец файла.
3. Что искать в логе:

   | Строка | Что значит |
   |---|---|
   | `in: ***1234 text` | Сообщение клиента дошло (номер скрыт, видны последние 4 цифры) |
   | `NOT DECRYPTED` | Сообщение не расшифровалось, в CRM ушла заглушка |
   | `processing stuck … last step: …` | Обработка зависала, программа переподключилась сама. На этом шаге и искать причину |
   | `baileys: …` | Шаги подключения |
   | `decrypt: N message(s) not decrypted - own phone/devices X, client chats Y, …` | Кто прислал нерасшифрованные сообщения |
   | `Stream Errored (ack)` через ~50 мин после подключения | Обработка снова висит |

4. Если чаты пропали, восстановить их через «Загрузить старые чаты заново» → QR (см. выше).

## Технические заметки (для разработки)
- Подробности по коду: `docs/HANDOFF.md` (записи 06.11 и 10.11), сообщения коммитов 30ccc18…552ce37.
- Тесты: в `connector/` команда `npm test` (118 проходят); в `crm/cf` команда `npm test` (134 проходят, 3 пропущены).
- **Особенности Baileys:**
  - Очередь `processingMutex` обрабатывает все входящие, квитанции и уведомления по одному и подтверждает их WhatsApp только после обработки.
  - `createBufferedFunction` включает буфер событий и сама его не выключает.
  - «Key used already or never filled» значит, что ключ сообщения уже использован (повторная доставка). Baileys отвечает NACK и сообщение выбрасывает.
- Нельзя менять браузер подключения (`Browsers.windows('Chrome')`, без syncFullHistory): с WIN32/Desktop WhatsApp сразу рвёт соединение (code 428).
- Windows PowerShell 5.1: лог владельцу удобнее отдавать через Блокнот. В окне Win+R не больше ~259 символов.
